# 学习任务: 两周内用 Rust 写一个团队内部可用的 CLI

## 为什么学

学习者不是为了泛泛学习 Rust，而是要在两周内交付一个团队内部可用的命令行工具。这个工具用于把日常重复操作标准化，减少团队成员手工复制、改名、校验和提交结果时的出错率。

## 本阶段学成什么样

两周后至少能交付一个 MVP CLI:

- 能通过 `--help` 清楚说明用途、参数和示例。
- 能读取一个输入文件或目录，并输出结构化结果。
- 能对缺失文件、格式错误、权限问题给出可理解的错误提示。
- 能在团队机器上通过二进制或 cargo 安装方式试用。
- 有 README、3 个真实使用例子和最小测试。

## 目标路由

类型: 交付型 + 能力型。

原因:

- 有明确期限: 两周。
- 有明确交付物: 团队内部 CLI。
- 需要边学边做，不适合先完整学完 Rust 再开始。
- 每轮学习都必须让 CLI 更接近可试用。

## 已有基础

- 会使用命令行和 Git。
- 有其他语言的基础，理解函数、错误、文件读写和测试。
- Rust 基础薄弱，容易被所有权、生命周期和 crate 生态拖慢。

## 约束

- 时间: 两周，前 3 天必须跑通端到端薄片。
- 范围: 只做一个内部工具，不做通用开源 CLI 框架。
- 质量: 错误提示要给团队成员看得懂，不直接暴露 Rust panic。
- 资料: 优先 Rust 官方文档、The Rust Book、Rust By Example、clap 文档。
- 验收: 至少 2 个团队成员能按 README 独立运行一次。

## 暂不做

- 不做 GUI。
- 不做插件系统。
- 不做复杂配置中心。
- 不追求覆盖 Rust 所有权系统的完整理论。
- 不优化极限性能，除非真实输入规模已经暴露瓶颈。

## 第一轮最小交付

第一轮不学习“大而全 Rust”。只做三件事:

1. 写出 CLI 的输入、输出、失败场景和验收标准。
2. 用 `clap` 设计一个能被团队理解的命令接口。
3. 做一个 thin slice: `cargo run -- process sample/input.txt --out sample/output.json`。

## 证据门槛

- E0: 看过 Rust CLI 教程。
- E1: 能解释 `Result`、参数解析和文件读取。
- E2: 能写出一个可运行命令，并处理至少 3 类错误。
- E3: 能把同一套 CLI 契约迁移到另一个团队任务，并修正参数设计。
